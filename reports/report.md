

## Задача
Проверить каталог `/app/target` на SSRF: вывести список файлов, запустить Semgrep с `p/python` и `p/owasp-top-ten`, прочитать исходники и найти sink'и `requests.get` с пользовательским URL.

## Результаты

### 1. Semgrep — SSRF не нашёл
Ни один из двух наборов правил не выдал находок класса SSRF. Обе находки (одни и те же в обоих прогонах) — `python.flask.security.audit.directly-returned-format-string`, `WARNING`, `/app/target/SSRF_service.py`, строки 29 и 30 (маршрут `/admin/delete`, возврат f-строки с `username`). Поле `snippet` в ответе Semgrep = `"requires login"`, т.е. фрагмент кода не отдавлен; код строк я проверил самостоятельно через `read_file`.

**Важно:** отсутствие SSRF-находок от Semgrep ≠ отсутствие SSRF. В этих наборах правил нет корректного источника/стока для `streamlit` + `requests.get` с пользовательским URL, поэтому вывод строится на ручном разборе.

### 2. Ручной разбор: найден sink с полностью управляемым URL

**`SSRF_streamlit_app.py`**

- Строка 39: `url = st.text_input("URL:", ...)` — **source**, значение целиком под контролем пользователя.
- Строки 7–8: единственный контроль —
  ```python
  BLACKLIST = ["127.0.0.1", "localhost", "169.254.169.254"]
  def is_banned(url): return any(badpattern in url for badpattern in BLACKLIST)
  ```
- Строка 46: **sink** — `r = requests.get(url, timeout=5, allow_redirects=True)`.
- Строки 48–55: **обратная связь (oracle)** — если `Content-Type` не `image/*`, сервер возвращает `HTTP <код> (<content-type>)` и **до 5000 символов тела ответа** в `st.code`. Это «полный чтение» SSRF, а не слепой.

Цепочка source → sink без разрывов: `st.text_input` → `is_banned` (подстроковый фильтр) → `requests.get` → тело ответа в UI.

**`SSRF_service.py`** — исходящих HTTP-запросов нет (`requests` не импортируется), т.е. SSRF-стока здесь нет. Файл ценен как **цель** внутренней сети:
- строки 15–23: `/admin` отдаёт в HTML `SECRET_TOKEN` (строка 6, захардкожен) и список пользователей;
- строки 25–31: `/admin/delete?username=...` — **изменяет состояние через GET, без аутентификации** (строка 30 — та самая находка Semgrep);
- строки 33–42: `/metadata` — имитация облачных метаданных (`169.254.169.254`) с тестовыми AWS-подобными ключами;
- строка 45: слушает `127.0.0.1:8080` — т.е. доступен **только** с самого хоста, куда SSRF и даёт доступ.

### 3. Обход фильтра (анализ кода, не подтверждён в рантайме)
`is_banned` — регистрозависимая проверка подстроки, поэтому обходится, как минимум:
- **регистром:** `http://LOCALHOST:8080/admin`, `http://LocalHost/` (в списке только нижний регистр);
- **альтернативными формами loopback:** `http://127.1/`, `http://2130706433/`, `http://0x7f000001/`, `http://0177.0.0.1/`, `http://[::1]/`, `http://0.0.0.0:8080/`;
- **DNS-именами на внутренний адрес:** `http://127.0.0.1.nip.io/`, собственный A-запись-домен, DNS rebinding;
- **редиректом:** `allow_redirects=True` (строка 46) — внешний URL, делающий 302 на `http://169.254.169.254/...` или `http://127.0.0.1:8080/admin`, фильтр вообще не видит;
- **иными приватными диапазонами,** которых нет в списке: `10.x`, `172.16-31.x`, `192.168.x`, внутренние сервисы по портам.

Оговорка: `file://` и подобные нестандартные схемы `requests` по умолчанию не поддерживает (`InvalidSchema`) — чтение локальных файлов через это **не** является подтверждённым вектором.

## Выводы

- **SSRF — подтверждён на уровне кода (высокая уверенность), не подтверждён в рантайме.** Сток `requests.get(url, allow_redirects=True)` с пользовательским URL и выводом до 5000 символов ответа — это классический неслепой SSRF; единственный контроль — регистрозависимый чёрный список подстрок, обходится минимум регистром, альтернативными записями `127.0.0.1` и редиректом. Статус: **уязвимость реальна, требует верификации на живом стенде** (я не отправлял запросов).
- **Влияние — высокое.** Рядом лежит Flask-сервис на `127.0.0.1:8080`, доступный только локально: через SSRF становятся доступны `/admin` (утечка `SECRET_TOKEN`), `/metadata` (имитация учётных данных метаданных) и `/admin/delete` (несанкционированное изменение состояния через GET без авторизации — SSRF работает как «руки» атакующего внутри сети). Плюс классический риск доступа к реальным метаданным облака и сканирования внутренней сети.
- **Побочные находки (вне рамок SSRF):**
  1. Захардкоженный секрет `SECRET_TOKEN` в коде и его отдача в HTML `/admin` — критично само по себе.
  2. `/admin/delete` — GET-эндпоинт, изменяющий состояние, без аутентификации и без CSRF-защиты.
  3. Находки Semgrep (строки 29–30, `directly-returned-format-string`, WARNING) — потенциальный отражённый XSS через `username`; требует ручной проверки с учётом экранирования шаблоном.
  4. `st.markdown(..., unsafe_allow_html=True)` со сторонним фоном — сниженный риск, но включённый raw-HTML.
- **Ограничения отчёта:** только SAST + ручной разбор; Semgrep SSRF-правил не содержит, DAST не выполнялся; вывод о возможности обхода основан на чтении кода, а не на полученных HTTP-ответах.

**Что дальше (по вашему решению):**
1. Дайте URL развёрнутого стенда (Streamlit + Flask) и подтвердите разрешение — проверю SSRF-цепочку в рантайме на разрешённых целях стенда.
2. Для Semgrep добавьте набор правил с явным SSRF-паттерном (`requests.get` с `request.args`/`st.text_input`) — иначе такие стоки будут стабильно пропускаться.
3. Рекомендации по исправлению: белый список доменов/схем вместо чёрного списка, разрешение DNS и проверка IP **после** резолва (с запретом loopback/link-local/privatespace), `allow_redirects=False` или проверка каждой редирект-цепочки, сетевая сегментация и egress-политика, обязательная авторизация на `/admin*` и перевод `/admin/delete` на POST, удаление секрета из кода в переменные окружения.
