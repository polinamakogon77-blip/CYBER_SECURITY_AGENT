## Результаты

### 1. SQL-инъекция в маршруте поиска товаров
- **Категория:** SQL Injection (UNION-based)
- **Severity:** HIGH
- **Локация:** `/app/juice-shop/routes/search.ts`, строка 23
- **Статус:** confirmed (на уровне исходного кода)

**Доказательство (фактический код):**
```ts
// строка 21
let criteria: any = req.query.q === 'undefined' ? '' : req.query.q ?? ''
// строка 22
criteria = (criteria.length <= 200) ? criteria : criteria.substring(0, 200)
// строка 23
models.sequelize.query(`SELECT * FROM Products WHERE ((name LIKE '%${criteria}%' OR description LIKE '%${criteria}%') AND deletedAt IS NULL) ORDER BY name`)
```

**Анализ потока данных:**
1. **Источник:** `req.query.q` — пользовательский вход из query-параметра `q` (маршрут поиска товаров, `GET /rest/products/search?q=...`).
2. **Преобразования:** единственная «защита» — обрезка до 200 символов (строка 22). Экранирования, валидации или параметризации нет. Ограничение длины не препятствует инъекции — для UNION-инъекции достаточно короткого payload.
3. **Sink:** `models.sequelize.query()` с шаблонной строкой — значение `criteria` интерполируется напрямую в SQL-текст. Метод `query()` Sequelize без bind-параметров не экранирует строку.

**Дополнительные признаки в коде:**
- Маркеры `vuln-code-snippet` / `vuln-line` и имена вызовов `challenges.unionSqlInjectionChallenge` и `challenges.dbSchemaChallenge` (строки 18, 23, 26, 44) — код сам помечает строку 23 как уязвимую.
- Логика чалленджей (строки 26–58) проверяет, содержатся ли в ответе поиска email/пароли пользователей (`UserModel.findAll()`) и определения таблиц из `sqlite_master` — т.е. приложение по дизайну допускает извлечение чужих данных через UNION-инъекцию в этом параметре.

**Ограничения проверки:**
- Выполнен только статический анализ; динамическая эксплуатация (UNION-запрос к базе) по заданию не проводилась.
- Эксплуатируемость подтверждена на уровне кода: отсутствие параметризации при наличии пользовательского ввода в SQL-строке.

**Рекомендация:**
Использовать параметризованный запрос, например:
```ts
models.sequelize.query(
  `SELECT * FROM Products WHERE ((name LIKE :q OR description LIKE :q) AND deletedAt IS NULL) ORDER BY name`,
  { bind: { q: `%${criteria}%` } }
)
```
либо запрос Sequelize с `where` и `Op.like`, чтобы значение передавалось как параметр, а не как часть SQL-строки.

## Выводы
- **Подтверждено:** в файле `/app/juice-shop/routes/search.ts` (строка 23) существует SQL-инъекция — пользовательский параметр `q` без экранирования/параметризации вставляется в SQL-запрос к таблице `Products`. Ограничение в 200 символов не является защитой.
- **Наиболее существенный риск:** несанкционированное чтение данных БД (в т.ч. учётные данные пользователей и схема БД, судя по логике чалленджей в том же файле).
- **Требует дополнительной проверки (не в рамках данной задачи):** динамическое подтверждение эксплуатации на разрешённом стенде.
- **Приоритет исправления:** параметризация запроса в `searchProducts()` — единственная и главная находка в анализируемом файле.
